What does this teach?

SHA-256 produces 256 bits, written as 64 hexadecimal characters. Small input changes typically change many output bits, often about half—not necessarily exactly half. Hashes are not decrypted; guessed inputs can be hashed and compared. Plain SHA-256 is not a password-storage scheme. Password hashing and salts will be a separate lesson.

    A digest describes bytes

    Encryption scrambles a message so someone with the right key can decrypt it. A cryptographic hash takes input bytes and produces a fixed-size digest. You do not decrypt the digest to recover the file.

    SHA-256 always produces 256 bits, usually written as 64 hexadecimal characters. The same input bytes always produce the same digest. A guess can still be hashed and compared, so a hash does not make a weak password strong.

    Follow a letter. Find the key.

    Learn a Caesar cipher by doing the shifts yourself. Predict a letter, decode a word, then recover a short message. Hints are available when you need them.

    The alphabet wraps around

    Encryption moves each English letter forward by the same number of places. After Z, continue at A. A shift of 3 means three moves, not three letters including the starting letter.

    LESSON 02 · PASSWORD STORAGE

    Why a password needs more than a hash

    Use a fictional account to explore fast hashes, unique salts and password verification. This is a teaching demo, not an account or password manager.

    This browser cannot run the password experiment here. Use HTTPS or localhost in an up-to-date browser.

    Fast hashes make guesses cheap

    SHA-256 is useful for checking file bytes, but it is designed to be fast. That lets someone test many password guesses quickly if stored hashes are exposed. It does not mean SHA-256 is broken.

    Password-hashing algorithms add a configurable cost to each guess. Strong, unique passwords still matter; adding a salt does not make a weak password unguessable.

    Why is plain SHA-256 alone unsuitable for storing passwords?

    Same password, different account records

    Both fictional accounts use harbor-lantern. Compare their plain SHA-256 digests, then generate a unique random salt and a PBKDF2 value for each account.

    Demo settings: PBKDF2-HMAC-SHA-256 · 600,000 iterations · 16-byte random salt · 256-bit output. The browser performs the work locally.

    Salts are stored alongside the derived values; they are not secret decryption keys. Unique salts prevent work from being reused across accounts, but each weak password can still be guessed.

    Does adding a salt make a weak password unguessable?

    Verify a guess without decrypting

    For account A, derive a value from a guess using the stored salt and settings, then compare it with the stored value. The original password is not recovered from the stored record.
